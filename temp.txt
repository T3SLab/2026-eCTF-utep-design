1. Unauthenticated permissions (most significant)
The receive_request_t sent by the receiver contains a permissions[] array that the listener uses to decide if the receiver is allowed to get the file (commands.c:452-458). These permissions are completely self-reported — any device on the UART bus can send a RECEIVE_MSG claiming arbitrary permissions. Without receiver authentication, the permissions check is trivially bypassable.

2. No receiver identity verification
By design you're not verifying the receiver, but this means any entity on the transfer bus can request files. If an attacker gets physical access to the UART, they can impersonate a legitimate HSM by simply crafting a RECEIVE_MSG with the right permissions. The one-way auth only proves to the receiver that the listener is legitimate — it says nothing about whether the receiver is legitimate.

3. No binding between auth and the request
The signature covers only the nonce — it doesn't commit to the slot, permissions, or any details of the file request. Auth succeeds then the listener proceeds with command->slot and command->permissions from the unverified RECEIVE_MSG. A MITM on the bus could in theory swap those fields between the request and the auth exchange.

Summary:
If your threat model is "I want to make sure I'm not receiving files from a rogue device pretending to be a valid HSM" — this is sound. If the threat includes a rogue device requesting files from a legitimate HSM (e.g., physical UART access), the unauthenticated permissions are the weak point to be aware of.
